# SkillReady 技能上岗单：14 天零花费验证计划

版本：2026-10-10。本文是待执行的实验计划与推广草稿，不代表已经发布、已经获得客户或已经收款。

目标是在 14 天内找到至少一位对具体交付有明确付费需求的客户。明确付费需求是对方确认服务范围、价格和预期交付时间，并愿意进入付款安排；实际到账另行记录。星标、浏览、口头称赞、免费试用都不算收入。

“零花费”指本轮不购买广告、域名、服务器、模型 API 或付费工具。开发、沟通、交付仍消耗时间，现有电脑与网络也有成本。免费发布渠道若出现收费要求，先保留本地演示，不为验证擅自付费。

## 产品事实与发布状态

SkillReady 的当前范围是：浏览器本地读取用户选择的文本，寻找静态线索，整理域名、环境变量名称和命令清单，生成内容指纹；由用户填写负责人、数据使用信息并勾选人工验收项，最后导出 Markdown / JSON。产品运行不依赖后端服务器或模型 API。

这些线索帮助整理接入资料，不构成对实际运行行为的验证。命令、域名或环境变量的出现本身不代表恶意；未发现线索也不能证明安全。只提供一个 SKILL.md，无法代表关联脚本、远程依赖和运行环境已经检查。文案不使用“首创”“保证安全”“自动通过企业合规”等表述。

## 先找谁、问什么

首轮聚焦 5–30 人的软件开发、AI 自动化交付或技术咨询团队，优先接触最近一个月确实引入过第三方 Skill 的技术负责人。个人爱好者可以提供可用性反馈，但要单独统计，避免将个人试用当成企业采购需求。

只通过自己的既有关系、允许分享项目的社区、以及对方主动联系开展验证。不群发私信，不把与项目无关的推广贴到他人 GitHub Issue，不自动发送任何消息。

访谈先了解真实经历，再演示工具：

1. 最近一次要让同事使用某个 Skill，具体是谁负责接入？
2. 当时如何确认用途、数据范围、外联服务和所需凭证？能否用脱敏材料举例？
3. 哪一步最花时间，或者因为谁没确认而停住？原来有没有表格或文档？
4. 导出上岗单后，对方还需要补什么，才能在自己的流程中使用？
5. 展示明确范围和试验报价后，询问是否愿意安排该项服务及时间；记录原话，不替对方推断预算。

不索取密码、API Key、未脱敏客户资料或完整生产环境。默认用公开 Skill 或客户本地操作演示。客户若愿意提供材料，应先约定范围与保存期限；不要让客户为了试用而发送秘密。

### 服务说明、验收与付款要点

这是一份沟通要点，不替代双方适用的正式合同；不涉及法律结论。

- **确认主体与需求**：写明服务提供方、联系人、客户联系人、Skill 名称/来源/版本、材料范围、用途、价格与交付日期。
- **开始条件**：客户已确认范围，提供必要的脱敏材料，并完成双方约定的首付款或付款安排；未满足时不承诺倒计时交付。

- **修改边界**：验收期建议为交付后 3 个工作日，包含一次合并反馈修订。新增 Skill、新版本、大幅增加文件或新增平台属于变更，先确认额外费用与时间。验收期是建议条款，需双方确认；不采用默认沉默即通过。

## 单位经济：先记时间，再判断值不值得做

以下全是预算假设，尚无真实成交数据。暂用每小时 ¥100 作为机会成本；可按自己的可持续收入要求修改。模型与服务器新增现金成本假设为 ¥0，支付手续费、税费及开票成本未知，不将其默认为零。

| 项目 | ¥299 服务 | ¥999 服务 |
| --- | --- | --- |
| 交付工时假设 | 整理 0.75h + 讲解 0.5h + 修改/管理 0.25h = 1.5h | 整理 3.5h + 辅导 1h + 修改/管理 1h = 5.5h |
| 交付时间成本 | 1.5 × ¥100 = ¥150 | 5.5 × ¥100 = ¥550 |
| 扣交付时间后的余额 | ¥299 − ¥150 = ¥149 | ¥999 − ¥550 = ¥449 |
| 每单获客时间假设 | 1h，即 ¥100 | 2h，即 ¥200 |
| 含获客时间后的余额 | ¥299 − ¥150 − ¥100 = ¥49 | ¥999 − ¥550 − ¥200 = ¥249 |
| 剩余还要扣除 | 支付手续费、税费、退款和固定投入分摊 | 同左 |

上表余额不是利润，也不包含前期开发和全部未成交访谈。若为了拿到 1 个 ¥299 订单总共用了 6h 获客，余额变为 ¥299 − ¥150 − 6 × ¥100 = **−¥451**，尚未扣其他费用。不能因为“没有买广告”就把获客当成免费。

每单记录实际总工时，使用同一公式重算：

`实际收入 − 实际交付小时 × 时薪假设 − 分摊获客小时 × 时薪假设 − 实际支付/税费/退款 = 当前假设下余额`

首轮优先卖固定范围的小服务。若多数客户要的是落地安装而不是接入资料，应另做范围更明确的安装辅导验证，不能直接扩大 ¥299 套餐。

## 记录表与停止门槛

用本地表格或文本人工记录即可，无需添加跟踪脚本。最少字段：匿名编号、用户类型、触达渠道、实际联系日期、最近真实问题、是否导入、是否导出、是否进入工作流程、是否再次使用、报价、反馈原话、明确付费意向、订单确认、实收金额、交付工时。不要保存无必要的聊天全文和敏感材料。

“合格访谈”需同时满足：对方确实参与团队 Skill 接入；能讲一个具体经历；讨论了当前做法。仅看过宣传或随口表示“不错”不计入。访谈和服务记录日期以实际发生为准。

下面是本轮实验门槛，不是统计学结论或收入预测：

- **第 7 天检查**：已完成至少 5 次合格访谈，却少于 2 人描述重复出现的接入资料问题，暂停功能开发，改访谈对象或问题定位。
- **可用性检查**：前 5 次实际操作中若 3 次以上无法独立完成导入到导出，先修复流程再增加触达；不要把操作受阻解释成没需求。
- **第 14 天继续条件**：完成约 10 次合格访谈，至少 3 人完成一份自己的上岗单、至少 2 人再次使用或在真实团队流程中采用，并至少 1 人明确接受某个具体服务的价格与范围。若还未到账，结果必须写“有付费意向，收入为 0”。
- **付费失败条件**：10 次合格访谈后没有明确付费需求，或大家只接受免费扫描，停止当前收费包装。保留工具，选择一个经访谈支持的更窄服务再试，而非直接开发订阅系统。
- **信任失败条件**：用户反复把结果当作安全保证，立即调整结果页和宣传；静态线索不能支撑的结论必须删除。
- **经济失败条件**：连续 2 单实际耗时超过预算 50%，或在合理分摊获客时间后无法覆盖自己的时间成本，暂停接新单，收窄范围或调整价格。
- **触达不足**：两周内未接触到足够目标用户，结论是“证据不足”，不是“市场验证成功”或“市场不存在”。下一步优先解决触达，不用新功能代替客户对话。

禁止伪造访问量、星标、订单、评价和客户 Logo；不购买虚假数据、不自买制造成交。不把自己的演示、重复刷新和测试导出计为用户活动。不把拟定报价计为订单，也不把收款截图草稿计为收入。
